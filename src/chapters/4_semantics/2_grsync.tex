\section{Formalization of \GRSync}
\label{sec:semantics:grsync}

This section details \GRSync, the synchronous kernel of \GRust used to define custom, reusable flow
operators called components. \GRSync is inspired by Lustre-like languages~\cite{%
    DBLP:conf/tase/ColacoPP17,%
    DBLP:conf/hybrid/BourkeP13,%
    DBLP:conf/emsoft/CohenGP12%
}, which are well-established tools for bridging the gap between the functional requirements and the
implementation of critical systems.

A core feature of traditional synchronous languages is the use of \emph{clocks} to explicitly define
when computations are performed. While powerful, mastering clock calculus often requires a deep
understanding of the language's formal semantics. Indeed, many of these languages provide
higher-level constructs like \kwf{automaton} or \kwf{switch} to ease the development of state-based,
efficient systems.
%
Following this principle of abstraction, in order to improve usability for engineers, \GRSync omits
explicit clocks and instead provides higher-level constructs, \kwf{when} and \kwf{match}. These
constructs are designed to model event-driven state machines---a common pattern requested by the
automotive industry---without exposing the complexity of fine-grained clock relations.

As a synchronous language, \GRSync adheres to the synchrony hypothesis: all equations within a
component are evaluated simultaneously, as if in a single, logical instant. While this model
simplifies reasoning about concurrency, it requires a strict discipline to prevent ill-defined
computations. This discipline is \emph{causality}, the property that an output at any instant can
only depend on inputs from the present or past. Enforcing causality is fundamental: it prevents
logical paradoxes, such as a value depending on itself at the same instant, and thus guarantees that
every component is executable.

This section provides a formal definition of \GRSync, structured as follows. We first define its
syntax (\Cref{sec:semantics:grsync:syntax}) and give a formal definition to the causality property
(\Cref{sec:semantics:grsync:causality}). We then provide two complementary semantic models: an
operational semantics describing step-by-step execution (\Cref{sec:semantics:grsync:opsem}), and a
denotational semantics defining behavior over time (\Cref{sec:semantics:grsync:denot}). Building on
this, we introduce a novel reactive type system (\Cref{sec:semantics:grsync:react_typing}), which
statically enforces the restrictions necessary for safe, event-driven execution. Finally, we
establish key theorems that validate our design (\Cref{sec:semantics:grsync:theorems}), including
proofs of productivity (\Cref{thm:semantics:grsync:theorems:productivity}), determinism
(\Cref{thm:semantics:grsync:theorems:determinism}), and semantic equivalence
(\Cref{thm:semantics:grsync:theorems:equivalence}), alongside the oversampling theorem
(\Cref{thm:semantics:grsync:theorems:oversampling}), which confirms the soundness of the reactive
type system.

\subsection{Discussion}
\label{sec:grsync:discussion}

The formalization of \GRSync reflects its design, which prioritizes simplicity, safety by
construction, and seamless integration into an event-driven architecture.

\paragraph{Implicit clocks}
A primary design choice is the omission of explicit, programmer-defined clocks, which distinguishes
\GRSync from languages like \Lustre or
\Signal~\cite{DBLP:conf/emsoft/ColacoP03,DBLP:conf/cdc/BenvenisteBGBGM01}.

In \GRust, the base clock of a component instance is generated by the \GRFRP service. The generated
clock implement the push-based execution strategy, with a logical tick occurring whenever an input
of the component has changed. This design automates the integration of the synchronous component
into the asynchronous environment.

Within a component, this base clock can be further refined to filter computations. For this, \GRSync
provides the control-flow constructs \kwf{match} and \kwf{when}. These serve as a more intuitive
form of clock filtering compared to the abstract clock operators of other languages. Because they
operate on data values rather than on the clocks themselves, they allow developers to express
conditional execution in a familiar way, while the language guarantees that the resulting sub-clocks
are valid by construction.

These design choices involve a deliberate trade-off. The absence of a multi-clock calculus makes
\GRSync less directly expressive for modeling complex, multi-rate interactions within a single
component. However, this limitation is by design, delegating such complexity to the asynchronous
\GRFRP service level.

\paragraph{Causality analysis}
Building on well-established principles from the synchronous language community, \GRSync
incorporates a static causality analysis. This compile-time check is critical for high-integrity
systems because it formally guarantees executability. By rejecting programs with instantaneous
feedback loops, the analysis ensures that every component is both productive, as proven by the
Productivity \Cref{thm:semantics:grsync:theorems:productivity}, and deterministic, as
confirmed by the Determinism \Cref{thm:semantics:grsync:theorems:determinism}.

\paragraph{Reactive analysis}
The main contribution presented here is the reactive type system, which distinguishes between
\emph{continuous} and \emph{discrete} flows. This system enables a static analysis to determine
whether a component is \emph{reactive}. This check is crucial because it serves as the formal safety
precondition for the entire architecture: it verifies that a synchronous component can be soundly
called by a push-based, asynchronous service. For any component passing this check, the Oversampling
\Cref{thm:semantics:grsync:theorems:oversampling} then provides the definitive proof, formally
establishing that this push-based execution is semantically equivalent to a conventional pull-based
model.

This formal equivalence is significant because it empowers the compiler to automatically generate
the integration layer between the asynchronous service and the synchronous component. This automated
approach contrasts sharply with conventional methods, where the programmer is responsible for
manually defining the base clock and sampling logic, often using dedicated languages like
Prelude~\cite{DBLP:journals/deds/PagettiFBCL11}. By generating this layer, \GRust leverages the
Oversampling Theorem to provide the formal proof that makes the architecture sound.

\paragraph{Summary}
In summary, the formal treatment of \GRSync establishes a sound foundation for reactive component
design. Causality analysis provides the basis for the Productivity and Determinism
\Cref{thm:semantics:grsync:theorems:productivity,thm:semantics:grsync:theorems:determinism},
ensuring all components are executable. The central contribution is
the reactive type system, whose soundness is confirmed by the Oversampling
\Cref{thm:semantics:grsync:theorems:oversampling}. This theorem formally justifies the automatic
integration of synchronous components into a push-based, asynchronous system, a key feature of
\GRust. Building on this synchronous foundation, the next section formalizes \GRFRP, the
asynchronous service-modeling kernel.
