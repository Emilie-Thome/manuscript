## V.3.a.i

### 1744-1749 

The term "preprocessing" is missing, "meta-programming" is too broad a notion though
it does include "preprocessing". A proc-macro macro is a preprocessing step taking place right after
parsing, i.e. once the text has been transformed into tokens but before it goes through static
analysis steps such as borrow-checking and type-checking. As you explain, it is a function takes the
token-tree stream given to the macro invokation `grust! { <tokens> }` into a stream of tokens
corresponding to actual rust code (potentially containing more macros to expand) that replaces the
whole macro invokation.

Also I'm not completely clear what the alternative to a proc-macro is. When you say "standalone
compiler", you mean a standalone tool that transpiles grust code to rust code, right? My remarks
assume this is what you mean.

(I don't think you absolutely need to distinguish between "compiler" and "transpiler", though doing
so is not a bad idea if it's concise.)

- "Seamless integration." Yes, but I think you're missing two key points which boil down to getting
- "a full ecosystem for free".
    + Writing grust code is done inside a normal rust file: (some) syntax highlighting and
    auto-completion through the Rust LSP (language server protocol) for free. With a standalone
    compiler, one would need to write syntax-highlighting extensions for various IDEs, and some form
    of LSP for auto-completion.
    Also compilation errors are directly source-mapped to user tokens, including borrow-checking and
    type-checking errors. (Though there is limited control on the shape of these errors, see the
    cons of the approach.)
    + Grust developers can use rust definitions easily, though the grust compiler can restrict and
    constrain this aspect. **This is a super important, major argument for this approach**, and I
    think it should be its own (short) paragraph.

- "Leveraging the Rust compiler." What you say does not really make sense: the alternative is a
standalone compiler that generates Rust code. Note that this does not really describe a compiler,
this is a "transpiler" which the proc-macro also is. The result of both approaches is the same,
the rust compiler will borrow-check, type-check, and optimize the code coming out of the compiler
either way.

This point would only stand if the standalone compiler approach would generate binary code
directly in which case yes you would need to do all the checking and optimization yourself. I
think you should remove this point altogether, or move it up to justify having Rust as a backend
(which is the case of the proc-macro and the standalone ~~compiler~~ transpiler).

- "Package management." Yeah, but you could do the same with the standalone transpiler, though it
would be more tedious.

There's something I don't understand: this paragraph is about what you can do with the resulting
rust code. Why do you discuss grust-std here, which is not about the code coming out of the
macro, it's more about being compatible with existing rust code (which is what this paragraph
should be about imho).

- "Simplified qualification path." Sure.

About the challenges of using proc-macros, I would say an issue is that there is no communication
between invokations of the proc-macro, *i.e.* grust compilation runs. This makes it difficult to
write part of a grust system somewhere and import it somewhere else. Traits such as Component
formalize the interface expected by the compiler, but "bad" developers can implement it by hand and
falsify the logic expected by the compiler.

Another challenge is that since everything happens before static analyses, in particular
type-checking, any checks we want to perform must create their own environment from scratch since
the normal rust environment does not exist at this stage yet.

## v.3.a.iv

### 1864-18651924

"a developer" → "developers". Always use plural if possible for people, that way you can
avoid dealing with their genre because the pronoun is just "them". With inclusive language you would
use "them" for a single person, but this may be a problem for queer-phobic readers. Ideally we would
just not care about them and their feeling, but some of them have power over us so just avoid the
problem by always using plural for people.
